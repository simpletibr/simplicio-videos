# ADR-0020: `install` universal e `update` iguais aos do simplicio-loop (a skill vai para o host; o checkout não é atualizado pelo CLI)

- **Status:** aceito. Implementado no PR "install universal e update igual ao simplicio-loop" (pedido direto do dono, sem issue, como os PRs #108 a #116). **Supersede** a decisão do [ADR-0017](ADR-0017-instalacao-atualizacao.md) sobre o `install` (o `.venv` com uv) e sobre o `update` de um checkout (`git pull --ff-only`).
- **Data:** 17/10/2026 (BRT)
- **Relaciona:** [docs/host/packaging.md](../host/packaging.md) (o que cada comando faz e toca) · [docs/how-to/install.md](../how-to/install.md) (passo a passo) · [ADR-0017](ADR-0017-instalacao-atualizacao.md) (instalação e atualização, superada em parte) · [ADR-0019](ADR-0019-login-compartilhado.md) (login compartilhado, mesmo método de porte) · [testar em Windows e macOS](../how-to/testar-em-windows-e-macos.md)

## Contexto

O simplicio-loop e o simplicio-video devem ter os mesmos comandos de operação. O PR #116 trouxe `login`, `logout`, `auth status`, o `doctor` em `simplicio.doctor/v1` e o `update --check` no contrato do loop, mas manteve duas decisões próprias, escritas como "padrão, a confirmar" no plano:

1. o `install` continuou sendo o `.venv` do checkout (uv, Python 3.12, extras), enquanto o `install` do loop **copia as skills para o host do agente** (`.claude/skills`, ou o `~` com `--global`) e grava um recibo de posse;
2. o `update` de um checkout continuou rodando `git pull --ff-only`, enquanto o do loop **recusa** (`git pull` e `bash scripts/dev_install.sh`, exit 2).

O pedido do dono desfez as duas, em quatro frases em sequência: "Coloca install, update, doctor, login, mesma coisa que fizemos no simplicio-loop e compatível com simplicio-runtime"; "Só olha simplicio-loop"; "Fazia igual estava no simplicio-loop"; "Universal". Universal quer dizer todos os agentes e hosts que o loop suporta e os três sistemas: Linux, macOS e Windows. Este ADR supersede, no ADR-0017, as decisões 1 a 4 (o `./install.sh` que chamava o `install`, o `.venv` com o registro `simplicio-install.json`, a idempotência pelo `install` e o `update` por `git pull --ff-only`).

## Decisão

1. **O `install` é o do loop.** `simplicio-video install` copia as skills empacotadas (`simplicio-video` e `simplicio-video-social`) para o host e grava o recibo `.simplicio-video/install-ownership.json`. Padrão: o projeto (`--target`, a pasta atual) em `.claude/skills`; com `--global`, o `~` (HOME, depois USERPROFILE, como o Runtime), e a skill vai para as **11 pastas** do `skill_sync.py` do loop (`.claude/skills`, `.codex/skills`, `.cursor/skills`, `.grok/skills`, `.agents/skills`, `.copilot/skills`, `.vscode/simplicio-skills`, `.config/opencode/skills`, `.config/amp/skills`, `.kiro/steering` e `.simplicio-loop/skills`), com o `--host` ignorado (como no loop). Em cada pasta vale a regra de posse da revisão do #117: o install cria o que falta (e o arquivo entra no recibo com o `sha256`), atualiza só a cópia que é do recibo e que ninguém editou, deixa em paz (`left_alone`) o que já existia ou que o usuário editou e nunca apaga um arquivo extra. Flags do loop: `--target`, `--global`, `--host`, `--dry-run`, `--check` (0 em dia, 10 pendente), `--json`, `--verify`, `--uninstall` e `--prune-project-copies`. O documento JSON é `simplicio.video-install-plan/v1`, o `simplicio.loop-install-plan/v1` com as mesmas chaves (`up_to_date`, `changes{created,updated,unchanged,left_alone}`, `owned`, `digest`, `host`, `version`, `resynced`).
2. **Os hosts são os do registro do loop.** O planejador do loop (`simplicio_loop/install/planner.py`) tem 12: `claude`, `codex`, `cursor`, `vscode`, `grok`, `kiro`, `antigravity`, `opencode`, `gemini`, `aider`, `simplicio_agent` e `openclaw` (mais `all`). Todos se aplicam a skills e todos foram portados. As skills vão sempre para `.claude/skills`; o arquivo de entrada do host (`AGENTS.md` para `codex`, `grok`, `antigravity` e `opencode`; `GEMINI.md`; `CONVENTIONS.md`; `.github/copilot-instructions.md`; `.kiro/steering/simplicio-video.md`) só é criado se ainda não existir, como na tabela `RUNTIMES` do `install_lib.py` do loop. `claude`, `cursor`, `simplicio_agent` e `openclaw` não precisam de arquivo de entrada. As pastas de skills que o `--global` instala são as do `skill_sync.py` do loop (11 pastas, as mesmas relativas ao HOME nos três sistemas).
3. **Só skills: o simplicio-video não tem hooks.** O loop copia também `hooks/` e regras de host (`simplicio-loop-operator-flow.md`); nada disso existe aqui, então não há `hooks` no `install`, nas ações do plano nem no help, e as regras de host (`rules`) ficam vazias no `resynced`, por contrato com as chaves do loop.
4. **Nunca sobrescreve o que não é dele.** Outras skills da pasta, um `AGENTS.md` seu e um arquivo que não é comum (pasta, FIFO, link simbólico) ficam em `left_alone`. O `--uninstall` remove só o que está no recibo **e ainda tem o `sha256` que foi gravado**, mais as pastas que o install criou e que ficaram vazias; um recibo adulterado (caminho absoluto, `..`, letra de unidade, caminho que o registro de hosts nunca produz, link que escapa do alvo, dono ou esquema desconhecido) é recusado antes de apagar qualquer coisa.
5. **A skill vai dentro do pacote.** A cópia que o `install` instala fica em `src/simplicio_video/data/skills/` e viaja no wheel; `skills/` na raiz do repo é o espelho que o plugin do Runtime lê, e um teste exige igualdade byte a byte entre os dois. **A fonte da verdade é a cópia do pacote**: edite lá e copie para `skills/`. Como o wheel vai para o PyPI (público e imutável), a skill ficou sem nome de cliente, sem identificador do dono e sem link relativo que só vale no checkout; a guarda de dados de cliente do #115 passa a cobri-la.
6. **O `.venv` com uv sai do `install`.** Vira `scripts/dev_install.sh` (Linux e macOS) e `scripts/dev_install.ps1` (Windows, PowerShell), com a lógica que estava no `install.py` e no `install.sh`: Node 22, ffmpeg com libass, 5 GB, uv (oferecido, só com sim), Python 3.12, extras, `web/` e o `doctor` no fim. O `install.sh` da raiz e o novo `install.ps1` são invólucros finos. Nenhum deles usa o python do sistema, o que fecha o bug B1 do #116 por construção (o `install.sh` rodava `python3 -m simplicio_video` num Python sem PyYAML). O `simplicio-install.json` e as opções `--python` e `--with` do `install` saem, sem compatibilidade.
7. **O `update` é o do loop.** Num pacote instalado por pip: `pip install --upgrade "simplicio-video==<versão>"` (PyPI; a versão vem da última release do GitHub) e, **depois**, `simplicio-video install --global`, que reinstala as skills nos hosts. Num checkout git ou instalação editável o `update` **recusa**: imprime `git pull` e `bash scripts/dev_install.sh` (no Windows, `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\dev_install.ps1`: o Windows de cliente vem com a política `Restricted`, e o `-ExecutionPolicy Bypass` vale só para esse processo; UNVERIFIED sem um Windows real) e sai com 2 (exit 2). O `git pull --ff-only`, o `git reset --keep`, o build de `web/` e a recusa de árvore suja do `update` saem. `--check` continua 0, 10 ou 2 e grava `update-check.json`; num checkout ele ainda pergunta ao git quantos commits são novos, e alterações locais não atrapalham mais (nada é puxado). `--force` e `--dry-run` têm o sentido do loop; o `--force` num pacote já em dia reinstala só o nosso (`--force-reinstall --no-deps`) e, com uma versão mais nova, roda o `--upgrade` normal (o `--no-deps` pularia uma dependência nova).
8. **O `doctor` não ganha linha de skills.** O `doctor_overview.py` do loop não tem uma linha para isso (as seções são `login`, `update`, `distribution`, `runtime`, `operators`, `disk`, `map-store` e `setup`), então o doctor daqui não cria uma. A linha `distribution` e a de `setup` continuam.
9. **Multiplataforma sem premissa POSIX.** A pasta pessoal vem de `HOME`, `USERPROFILE` e `Path.home()`, nessa ordem, em todo sistema; a cópia nunca usa link simbólico (no Windows exige privilégio); a escrita é atômica (arquivo temporário na mesma pasta e `os.replace`); arquivos de texto levam `encoding="utf-8"`; os testes simulam `linux`, `darwin` e `win32`, e os que precisam de arquivos POSIX de verdade são marcados.

## Diferenças de propósito em relação ao loop

O contrato é o do loop; estas são as únicas diferenças, todas para o lado mais seguro ou mais claro:

- **`up_to_date` no `--json`** diz só do alvo, como no loop. No loop o exit do `--check` era 10 por causa de uma cópia desatualizada de outro host; aqui o `install` não muda essa cópia, então ela não torna nada pendente.
- **`--prune-project-copies` sem `--global`** é um argumento inválido (exit 2); no loop é ignorado em silêncio. O `prune` recusa um recibo adulterado e não entra numa pasta de skill que é link simbólico (o dono costuma apontar `.claude/skills/simplicio-video` para um clone).
- **Link simbólico**: o arquivo que é link (um `AGENTS.md` que aponta para o `CLAUDE.md`) fica em `left_alone`; uma pasta que o install cria que é link é **recusada** (exit 2, nada escrito), e a pasta base (`~/.claude`) pode ser link de dotfiles (regras abaixo). O loop escreveria no alvo do link.
- **`--json` em todos os modos.** `--verify`, `--uninstall` e o erro também imprimem UM documento (`status` diz a forma: `verified`, `failed`, `removed`, `error`); o loop imprime texto nesses casos.
- **O recibo guarda o `sha256`, o `--verify` compara os arquivos, o `install.lock` serializa e a regra de posse vale nas 11 pastas do `--global`** (cria o que falta, atualiza só o que é nosso e não editado, nunca apaga): a revisão do #117 (seção seguinte). O loop não faz nenhuma das quatro; o `resync` dele sobrescreve a cópia do host e apaga o que saiu do pacote.
- **Escrita atômica** e leitura sem travar em FIFO (`O_NONBLOCK` e `fstat` no mesmo descritor); o loop usa `write_bytes`.
- **Recibo `v1`.** É o primeiro recibo do video (`simplicio.video-install-ownership/v1`); o `v2` do loop existe porque houve um `v1` antes dele.
- **Textos em português** com acentos; o recibo e o JSON têm as mesmas chaves.

## Revisão independente do PR #117 (2e3d95c): o que mudou e por quê

A revisão (read-only, HOME e PATH isolados) reprovou o PR com 2 bloqueantes, 6 importantes e 12 menores, todos medidos. As regras abaixo saíram dela. O recibo é um arquivo do repositório do usuário, e um repositório clonado pode ser hostil; o loop tem o mesmo defeito, mas este PR promete "nunca apaga o que não é dele".

1. **O recibo guarda o `sha256` de cada arquivo (B2).** Um arquivo só é apagado (`--uninstall`, `--prune-project-copies`) ou sobrescrito (um `install` depois) quando está no recibo e o `sha256` atual é o gravado. O `AGENTS.md` em que o usuário escreveu as regras dele não é mais apagado: fica `left_alone`, com um aviso. Um `install` seguinte também o tira do recibo.
2. **Só os caminhos que o registro de hosts produz (B2).** O recibo pode nomear as pastas das skills (`.claude/skills/simplicio-video*/...`), os valores de `HOST_ENTRY` e o próprio recibo, e nada além. Um **recibo plantado** num repositório clonado (`.git/config`, `src/app.py`, `.ssh/authorized_keys`, um byte nulo, um texto gigante) faz o `--uninstall` e o `--prune-project-copies` o recusarem inteiro (exit 1, nada é apagado); um `install` por cima dele o ignora, avisa e grava um novo, então não herda os caminhos.
3. **O que já existia nunca é tomado (I5).** O primeiro install não sobrescreve uma `SKILL.md` customizada (`left_alone`) e uma cópia idêntica do usuário só conta como `unchanged`, fora do recibo: o `--uninstall` nunca a apaga.
4. **O `--global` e as 11 pastas (I1).** A revisão mediu um `minhas-notas.md` do usuário sumindo de `~/.claude` e de `~/.codex` (o `resync` do loop apaga o que saiu do pacote) e o `update` do pip fazia isso sozinho ao chamar `install --global`. Uma primeira correção se limitava a relatar as cópias dos outros hosts; o dono recusou, porque tirava uma função do loop e reduzia o "universal". O que vale: o `install --global` instala e atualiza a skill nas 11 pastas do loop, com a regra de posse. **Cria o que falta** (o arquivo entra no recibo com o `sha256`). **Atualiza só a cópia que é do recibo e que ainda tem o `sha256` gravado** (nossa, não editada), quando o pacote tem uma versão mais nova. **O que já existia fora do recibo, ou que o usuário editou, é `left_alone`:** nunca é sobrescrito, mesmo idêntico (aí só conta como `unchanged`, sem entrar no recibo). **Nunca apaga um arquivo extra** do usuário dentro dessas pastas, nem o que saiu do pacote. O `--check` sai com 10 quando uma cópia nossa e não editada está desatualizada (ou falta), e a cópia alheia antiga não o deixa pendente; `up_to_date` volta a considerar as 11 pastas, como no loop. O `--uninstall` remove só o que é nosso. Uma pasta secundária que é link (um `~/.config/opencode` movido para um repositório de dotfiles) é pulada com um aviso e não derruba as outras; `~/.claude/skills` que é link continua recusando tudo (item 6). O `update` do pip, ao chamar `install --global`, continua seguro por isso.
5. **O `--prune-project-copies` (I2).** Só poda o recibo do projeto, com o `sha256`. Com o alvo igual ao home sai com 2, e as pastas da instalação global ficam protegidas mesmo quando o `.claude` do projeto é um link para o do home.
6. **Links (I3).** Cada pasta que o install cria (`.claude/skills`, a da skill, as de dentro dela e `.simplicio-video`) nunca é link: com link o install recusa (`InstallRefused`, exit 2, motivo claro, nada escrito). A **pasta base** do host (`~/.claude`, `.github`, `.kiro`) **pode** ser link, o caso de quem guarda o `.claude` num repositório de dotfiles: o install a resolve uma vez, opera no caminho real e grava no recibo (`bases`), e o `--uninstall` recusa se o link agora aponta para outro lugar. A junção do Windows vale como link pelo atributo de ponto de reparse do `lstat`, também no Python 3.10 e 3.11 (UNVERIFIED num Windows real).
7. **`--verify` (I4).** O do loop só confere a versão do plano (`{ok, version, digest}`) e dava ok para um alvo nunca instalado, uma skill adulterada e um recibo lixo. Este compara o disco com o recibo e com o pacote, mantém as chaves e o exit 1 do loop, e acrescenta `problems`: sai com 1 e `ok: false`.
8. **Comando do PowerShell (I6).** `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\dev_install.ps1`: a política padrão do Windows cliente é `Restricted` e `powershell -File x.ps1` para com "running scripts is disabled". O `Bypass` vale só para esse processo (o instalador oficial do uv faz o mesmo). UNVERIFIED sem uma máquina real; não sei se basta com a política travada por Diretiva de Grupo.
9. **Trava (m2).** `.simplicio-video/install.lock` (`0600`, o mesmo mecanismo do `login.lock`, espera de 10 s) serializa os installs, desinstalações e podas no mesmo alvo. Sem ela, três installs ao mesmo tempo deixavam o arquivo de entrada fora do recibo em 13 de 15 rodadas. O `--dry-run`, o `--check` e o `--verify` não a tomam.
10. **Menores.** Byte nulo no recibo vira erro claro (m1); `update --force` usa `--force-reinstall --no-deps` só sem versão nova (m4); o help diz que o `--host` é ignorado com `--global` e que um `AGENTS.md` que já existe não recebe apontador (m6); o schema do recibo restringe os caminhos (m8); `-With` aceita a lista do PowerShell (m9); o `.gitignore` cobre as skills copiadas na raiz (m10); um disco que falha no meio deixa um recibo coerente (m11); o `update` num Python sem pip diz `uv tool upgrade` (m12). **Fora:** m5 (erro do argparse com `--json` sai sem documento, igual ao loop) e dois detalhes de forma do JSON em relação ao loop (`ensure_ascii` e o `schema` de `pruned_project`).
11. **A segunda revisão (head a342a1c: 0 bloqueantes, 3 importantes, 10 menores).** (I1) Uma escrita que falha no meio de um update não tira mais o NOSSO arquivo do recibo: o `carry_forward` mantém, com o `sha256` antigo, tudo o que a execução não tornou nosso de novo (o arquivo antigo está intacto no disco e continua sendo nosso). (I2) O `update` do pip chama `install --global`, que instala ou atualiza a skill nas 11 pastas de hosts sob o home e cria as que faltam; help, how-to e skill diziam que só a `~/.claude/skills` era tocada. (I3) Nove mutações da re-revisão que sobreviveram ganharam teste vermelho. (a) Um `bases` forjado num recibo de projeto: em vez de recusar `bases` fora do alvo, o que quebraria o `.claude` de dotfiles que é link legítimo, o uninstall de projeto usa a mesma cerca do `--prune-project-copies` (as 11 pastas do home nunca perdem arquivo por ele). (b) `--global` com HOME ausente, relativo, `~`, `/` ou inexistente sai com 2, sem criar pasta. (c) Um recibo sem `sha256` (o build do head 2e3d95c) é inválido, com mensagem verdadeira. (d) `--verify` com `.simplicio-video` em link diz o caminho, sem "Nada foi escrito". Ficam para depois: TOCTOU (abrir por `dir_fd`), o `python -m pip` do `update` com o diretório atual no `sys.path` (vem da `main`), o erro do argparse com `--json`, `ensure_ascii`, a corrida de apagar o `install.lock` e o modo `0700` de `.simplicio-video`.

## Consequências

- Quem usava `./install.sh` continua usando: ele chama `scripts/dev_install.sh` com as mesmas opções. Quem usava `simplicio-video install` para o `.venv` passa a rodar `bash scripts/dev_install.sh`; o `install` agora é o que põe a skill no agente. Isso **quebra** `install --python`, `install --with`, `.venv/simplicio-install.json`, `install --check` do `.venv` e o `update` que puxava: CHANGELOG, `Mudanças que quebram`.
- `pip install simplicio-video` basta para o `install`: a skill vem no wheel. O wheel não ganha dado de cliente nem README (guarda do #115 e `twine check --strict`).
- O `update` de um checkout fica manual: `git pull` e `bash scripts/dev_install.sh`. O `doctor` continua avisando que há versão nova, e o aviso aponta para esses dois comandos.
- O custo é manter um porte: se o loop mudar o contrato do `install`, os dois divergem até alguém reportar. Os módulos dizem de qual commit do loop vêm (`2034e2d`).
- **UNVERIFIED.** Windows e macOS reais não foram rodados: o `scripts/smoke_so.py` agora exercita também o install num alvo temporário (`--check`, `--dry-run --json`, `--verify`, o install, o `--check` em dia e o `--uninstall`) e fica à espera de alguém rodar lá. O `scripts/dev_install.ps1` e o `install.ps1` são PowerShell escrito sem PowerShell à mão: **nunca foram executados**, só lidos por testes estáticos. O Runtime real também não foi chamado: o `install` não precisa dele, e o `login` segue com o Runtime falso dos testes.
- Fora do porte, de propósito: os hosts "listed" do catálogo do loop que só o `install_lib.py` do checkout escreve (o `install` empacotado do loop também não os anuncia), as regras de host e os hooks (o video não tem), e o `update` de binário (não há binário).

## Alternativas descartadas

- **Manter o `.venv` no `install` e o `git pull` no `update` (o padrão do plano do #116).** É o contrário do pedido do dono: dois comandos com o mesmo nome e semânticas diferentes nos dois produtos.
- **Deixar o `skill_sync` apenas relatar as cópias dos outros hosts (a primeira correção do #117).** Era seguro e tirava uma função do loop: o dono pediu "Universal" e "igual ao loop". A regra de posse dá a mesma segurança sem perder a função.
- **Escrever hosts novos além do registro do loop.** Os 12 do planejador bastam para o pedido ("o que o loop suporta"); acrescentar outros é uma linha na tabela `HOST_ENTRY` quando o loop acrescentar.
- **Link simbólico em vez de cópia.** No Windows exige privilégio e quebra quando o clone é movido.
- **Duas fontes da verdade para a skill.** Uma cópia em `skills/` e outra no pacote sem teste de igualdade divergem; com o teste, a do pacote manda.
